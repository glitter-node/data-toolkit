# v0.1.9 — SQLite job management

- `GET /api/jobs/{id}` requires `X-Job-Token`; returns progress (0–100), state, timestamps, result size, download availability, and error details.
- `DELETE /api/jobs/{id}` requires `X-Job-Token`; only terminal jobs may be deleted. Deletes the SQLite record and its output file.
- `GET /api/jobs/{id}/download` accepts `token` query parameter for backwards compatibility and now streams with FileResponse. Job-history UI uses `X-Job-Token`.
- SSE retains the existing token query parameter and includes progress/status metadata. Treat SSE URLs as sensitive; avoid logging query strings at the reverse proxy.
- No public job listing. Invalid credentials return 404. Tokens are stored as SHA-256 hashes.
- Progress is stage-based (queued 0, running 10–25, converted 85, completed 100), not byte-based.
- Existing SQLite databases are migrated by adding progress, result_size and finished columns.
- Cleanup runs at application startup; terminal records and result files are removed after `JOB_TTL_SECONDS` measured from completion. Long-running jobs are not deleted.
- Active jobs must be cancelled before deletion. Server restart marks queued/running jobs failed.
- The external form field `schema` is retained while Python uses `validation_schema`.
- Download availability is calculated from state and file presence. Job history requires an explicit ID and token.
- Automatic periodic cleanup is not provided; restart triggers cleanup. A future scheduled maintenance process may be added.
